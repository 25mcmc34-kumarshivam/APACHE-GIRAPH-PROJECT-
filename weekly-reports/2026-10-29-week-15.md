### Current input contract

The current `BurningScheduleTextInputFormat` expects **plain UTF-8 text**,
one vertex per line, with whitespace between fields:

```text
vertex_id source_round neighbour_id:weight neighbour_id:weight ...
```

For example, one scheduled four-vertex path can be saved as
`datasets/my-burning-case-01/part-01.txt`:

```text
1 1 2:1
2 0 1:1 3:1
3 0 2:1 4:1
4 2 3:1
```

Here vertices 1 and 4 ignite in rounds 1 and 2; `0` means the vertex is
not a selected ignition source. The `:1` is the edge-weight field required
by the reader, although this unweighted burning computation spreads **one
edge per round** and does not use that weight as a distance or probability.
For this example the predicted final rounds are `1 B 1`, `2 B 2`,
`3 NB -1`, `4 B 2` (tab-separated in output). The schedule ends after
round 2, before fire can reach vertex 3 in round 3.

All parts together form **one graph**. Every vertex ID must be defined once
across those parts; each neighbour ID must have its own vertex record.
This experiment treats the graph as undirected, so every `u v:1` must have
a matching `v u:1`. Put exactly one new source in each round `1, 2, ...`
with no skipped rounds. A chosen source must not have burned in an *earlier*
round. Lines with headers, comments, JSON, CSV columns or missing
`neighbour:weight` tokens are not supported by this Giraph reader. Keep
only graph records in the HDFS input directory. For a vertex with no edges,
the record is simply `vertex_id source_round`.

There are two ways to prepare a case on the **Windows laptop**:

1. **Your own sequence:** create `datasets/my-burning-case-01/part-01.txt`
   (and `part-02.txt`, etc. if desired) in the **scheduled** format above.
   You decide the source round in column 2.
2. **Random, not optimized:** create an **unscheduled** folder with only
   `vertex_id neighbour_id:weight ...` lines (for example `1 2:1`,
   `2 1:1 3:1`, `3 2:1`). Then run the preparer below. It inserts column 2
   and records the chosen sources in `selection.json`. This is a seeded
   random choice from eligible unburned vertices, not an optimal or greedy
   search. If it cannot find an eligible source for a requested round, it
   stops with an error; choose fewer rounds or inspect the graph.

```powershell
$repo = 'G:\swami sir\APACHE-GIRAPH-PROJECT'
$plain = Join-Path $repo 'datasets\my-plain-graph-01'
$scheduled = Join-Path $repo 'datasets\my-burning-case-01'
# First create the unscheduled part-*.txt files in $plain using an editor.
# $scheduled must not already exist; choose a new case name on a repeat.
python "$repo\scripts\prepare_random_burning_input.py" $plain $scheduled --rounds 3 --seed 12345
```

If you wrote the source rounds yourself, skip the preparer and set
`$scheduled` to your already-created scheduled folder. The following
commands work for **either** route. The validator checks format, duplicate
vertices, missing reverse edges and the round sequence. Do not proceed if

The GitHub repository stores source, notes, selected inputs and evidence; Hadoop/Giraph do not read the GitHub pages directly.

## Large real-world edge-list experiment: Web-Google subgraph

We next tested a real SNAP edge list instead of another hand-built graph.
The original `web-Google.txt` has 875,713 vertices and 5,105,039 directed
edges, so it was not uploaded to GitHub or sent directly to the burning
reader. [`convert_snap_edge_list.py`](../scripts/convert_snap_edge_list.py)
kept IDs below 100,000, converted the retained edges to an undirected graph,
removed duplicate/self-loop edges, selected the largest connected component,
and split it into four parts. The resulting experiment had 9,625 vertices
and 14,511 undirected edges.

Important size clarification: `--max-node-id 100000` was an ID filter, not
a request for exactly 100,000 output vertices. The filtered graph contained
multiple components; the converter retained its largest connected component,
which contained 9,625 vertices. We therefore describe this as a 9,625-node
subgraph experiment, not a 100,000-node experiment.

We copied the four scheduled parts to HDFS at
`/user/mca2025/giraph_learning/web_google_9625_burning_input`. Six random
eligible source rounds were generated with seed `20261104`:
`35524:55197:63686:84985:3677:38948`. This was a reproducible random
baseline, not greedy or optimal selection. Python predicted 131 burned and
9,494 unburned vertices. Giraph wrote
`/user/mca2025/giraph_learning/web_google_9625_burning_output/part-00000`;
`diff -u` returned **0**, and the actual copied output contains the same
9,625 rows. The saved input, prediction, round tables and actual TSV are in
the [large Web-Google result folder](../results/web-google-9625-burning-20261029/).

This experiment also demonstrated why an external edge-list converter is
needed: SNAP uses `source<TAB>target`, while the current Giraph burning
reader requires `vertex_id source_round neighbour_id:weight ...`. The
converter and its tests are now part of the repository. The original
72-MB edge list remains outside Git; only reproducible metadata and the
manageable converted experiment are committed.

Six rounds were a deliberately small first run to verify the large-graph
pipeline. They were not an algorithmic limit. In the current round model,
if there are `k` ignition rounds, the first source has up to `k-1` edge hops
to spread by the end, the second has up to `k-2`, and the final source has
radius zero. Thus the six-round run had radii `5,4,3,2,1,0`. The next
scaling experiment should construct a genuinely approximately 100,000-node
connected input and choose `k` according to the faculty's burning-sequence
rule, rather than silently treating six as the final model.
