At first `jps` showed only the Java process-list utility, and `yarn node

```bash

```

The successful check showed `NameNode`, `DataNode`, `SecondaryNameNode`,
`ResourceManager`, `NodeManager` and `Jps`, followed by one YARN node in
`RUNNING` state and zero containers. We did not start a second NodeManager
when one was already present.

On the lab account we made the local receiving directory:

From the Windows repository we used `scp.exe` to transfer the 72-MB

```powershell

  'G:\swami sir\web-Google.txt\web-Google.txt' `
```

The first converter command exposed that the script had not transferred; we
copied it and reran. Later, the random-schedule command exposed two missing
helpers, so we copied `prepare_random_burning_input.py` and
`find_small_graph_burning_sequence.py` as well. These errors and fixes are
also described in the chronological section below.

The official SNAP `web-Google.txt` edge list was inspected. It contains
875,713 vertices and 5,105,039 directed edges and is approximately 72 MB in
our transfer. It was intentionally kept outside GitHub because it is raw
source data, not a project result.

The new [`convert_snap_edge_list.py`](../scripts/convert_snap_edge_list.py)
converter was added to the repository and tested. It reads SNAP's two-column
edge format, removes self-loops and duplicates, converts the retained graph
to undirected adjacency, keeps the largest connected component and writes
multiple `part-*.txt` files. All 42 repository tests pass.

For the first safe large-graph baseline, IDs below 100,000 were considered.
The largest connected component in that range contained 9,625 vertices and
14,511 undirected edges. Six reproducible random eligible sources were added
with seed `20261104`:

```text

```

The six-round Python prediction and the fresh Giraph result matched exactly:
`diff -u` returned exit code `0` for all 9,625 rows. The final result was
131 `B` and 9,494 `NB -1`.

## Important interpretation

The `--max-node-id 100000` option was an ID bound, not a request for exactly
100,000 output vertices. The connected-component filter explains why the
verified result has 9,625 vertices. Six rounds were a first pipeline test,
not the final burning model. With `k` source rounds, the first source has
maximum radius `k-1`, the second `k-2`, and the last source radius `0`.
The six-round test therefore used radii `5,4,3,2,1,0`.
