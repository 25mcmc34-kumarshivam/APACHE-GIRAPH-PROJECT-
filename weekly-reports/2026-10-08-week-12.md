# Week 12 progress report — 2–8 October 2026

This week we tested Graph Burning with ignition vertices chosen by us,
without using a program to search for a good sequence. In the previous
experiments, we had already made Giraph read the ignition schedule from
the graph files and report when each vertex first burned. This experiment
checks whether that implementation also gives the expected answer for a
legal but non-optimized choice of sources.

## Why we chose a different source sequence

Sir had asked why we were already using a source-finding approach. We set
that question aside and selected vertices **1, 9 and 5** by hand for rounds
1, 2 and 3 on our nine-vertex path. The choice is deliberately not
optimized. We wanted to check that the Giraph program still behaves as
expected even if the chosen vertices do not burn the whole graph within
three rounds. We are calling this sequence *hand-picked*, not random:
we did not use a random-number generator.

## How we ran it

We used the same path graph as before:

```text
1 -- 2 -- 3 -- 4 -- 5 -- 6 -- 7 -- 8 -- 9
```

The three text files mark vertex 1 for round 1, vertex 9 for round 2 and
vertex 5 for round 3. On 6 October we:

1. Started HDFS and YARN as `hduser` after checking that their processes
   were not running. YARN then showed one healthy NodeManager.
2. Transferred the three graph parts from
   `datasets/graph-burning-path-9-hand-picked/` to a local directory under
   `/home/mca2025/`, then uploaded them as `mca2025` to the HDFS directory
   `/user/mca2025/giraph_learning/graph_burning_path9_hand_picked_input`.
   The input check found nine vertices, eight undirected connections and
   the source order `1:9:5`.
3. Ran the existing input-driven Giraph program as `mca2025`:

   ```bash
   bash "$HOME/giraph/run_graph_burning_from_input.sh" \
     /user/mca2025/giraph_learning/graph_burning_path9_hand_picked_input \
     /user/mca2025/giraph_learning/graph_burning_path9_hand_picked_output
   ```

   We used `bash` because the transferred runner did not have executable
   permission. No Java source had changed since the previous build, so a
   Maven rebuild was not needed. The source IDs came from the input files;
   the optional greedy source-finding script was **not** used.

YARN reported application `application_1790779476667_0001` as
**FINISHED / SUCCEEDED**. The actual HDFS output is preserved in
`results/graph-burning-path-9-hand-picked/part-00000.txt`.

## Result and explanation

```text
1  B   1
2  B   2
3  B   3
4  NB -1
5  B   3
6  NB -1
7  NB -1
8  B   3
9  B   2
```

Round 1 burns source 1. In round 2, fire from 1 reaches 2 while source 9
ignites. In round 3, fire from 2 reaches 3, fire from 9 reaches 8, and
source 5 ignites. Vertices 4, 6 and 7 are still unburned after the **third
and final** round, so they show `NB -1`. The output matches the calculation
we wrote **before** running Giraph. It demonstrates correctness of this
small experiment, not a proof of large-scale performance.

The Python input checker gave us a prediction to compare against the
Giraph result; it did not choose the sources. Another helper converted the
raw numeric Giraph values into the readable `B` and `NB` columns. The
Java input reader and Giraph computation still performed the graph job.
The code and commands are explained together in
`docs/WEEK-11-INPUT-DRIVEN-BURNING-SELF-CONTAINED-STUDY.md`.

## What we learned and what to discuss next

Our three runs now give us a useful comparison. The `3:8:6` schedule
burned the full path in three rounds. With `2:8`, five vertices remained
unburned after two rounds. With the hand-picked `1:9:5` schedule, three
vertices remained unburned after three rounds. The result depends on
**which vertices we choose and how many rounds we allow**; a legal source
sequence does not automatically cover the whole graph.

We would like to ask Sir whether to continue with more hand-picked source
sequences, generate truly random sequences, or move to a larger dataset.
We have not implemented random or optimal source selection in this new
input-driven program.
